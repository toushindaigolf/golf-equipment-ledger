# Supabase Phase 3-3 端末データ移行

Phase 3-3では、ログイン前に `golf-equipment-ledger-v1` へ保存した用品を、ユーザーが明示的に操作した場合だけSupabaseへ移行します。ログインだけでは移行しません。

## Supabaseへ適用する変更

Phase 3-1のマイグレーション適用後、次を適用してください。

```text
supabase/migrations/20260827000100_add_equipment_source_id.sql
```

追加される内容は次のとおりです。

- `public.equipment.source_id text null`
- `unique (user_id, source_id)`

通常のクラウド登録用品は `source_id = null` です。端末から移行した用品だけ、元のlocalStorage IDを `source_id` に保存します。PostgreSQLの一意制約ではNULLを複数保持できるため、通常登録には影響せず、同じユーザーが同じ端末用品を再移行した場合だけ重複を防止できます。

既存のRLSポリシーは `user_id = auth.uid()` のまま利用します。Service Role Keyは使用せず、`user_id` は認証中ユーザーからRepository内部で設定します。

## 移行手順

1. 端末内に実データがある状態でログインする
2. 移行案内の端末件数とクラウド件数を確認する
3. 必要に応じて「JSONバックアップ」を押す
4. 「クラウドへ移行する」を押す
5. クラウド既存データがある場合は、端末優先・クラウド優先・キャンセルから選ぶ
6. 件数と具体的な影響を確認して移行する
7. 成功件数・確認済み件数・失敗件数を確認する

移行開始時には必ず、次のメタ情報を含むJSONバックアップをダウンロードします。

- 作成日時
- アプリ名
- データ件数
- 元のlocalStorageキー
- 用途 `pre-cloud-migration`
- 用品データ本体

ファイル名は `golf-equipment-ledger-backup-YYYY-MM-DD.json` です。このバックアップは既存の復元パーサーでも読み取れます。

## 競合時の扱い

- クラウド0件: 端末用品を追加する
- 端末優先: 同じ `source_id` の移行済み用品だけを明示確認後に更新する
- クラウド優先: Supabaseを変更せず、端末データを保持して移行を保留する
- キャンセル: どちらのデータも変更しない
- `source_id` がないクラウド固有用品: 常に保持する

用品名や価格だけで同一判定は行いません。判断できないクラウド用品を自動更新・削除しないためです。

## 中断・失敗時

移行は用品単位で処理します。ブラウザを閉じたり通信が切れたりしても元のlocalStorageは削除しません。再実行時は `(user_id, source_id)` の一意制約と移行前比較により、完了済み用品を確認済みとして扱います。

移行状態は用品データとは別の次のキーに、Supabaseユーザーごとに保存します。

```text
golf-equipment-ledger-migration-v1:<user_id>
```

保存する状態は、移行中・完了・一部失敗・失敗・保留と、件数、最終実行日時、バックアップ日時、失敗したsource IDです。用品本体のlocalStorageキーと形式は変更しません。

## 実環境で確認すること

1. 追加マイグレーション適用前は移行を実行しない
2. 端末データのみ、クラウドデータのみ、両方ありの3パターンを確認する
3. 2ユーザーを用意し、別ユーザーの用品が見えないことを確認する
4. 移行途中で通信を切り、端末データが残り再試行できることを確認する
5. 移行後に再読み込みし、二重登録されないことを確認する

ログイン中の一般的なJSON復元、localStorage削除、完全自動同期、競合の完全自動解決、Pro権限、決済は今回の対象外です。
